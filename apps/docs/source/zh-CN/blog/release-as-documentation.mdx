# 把发布说明写成产品文档

发布说明不是提交记录的另一种排版。它要回答三个更接近用户的问题：发生了什么、这对我有什么影响、我是否需要采取行动。

## 从变化清单转向用户结果

一份提交列表通常围绕实现组织，例如“重构路由解析器”或“新增 metadata 字段”。发布页面应把它们翻译成可验证的用户结果：页面可以继承导航组布局，作者可以在单页覆盖布局，版本记录可以使用结构化组件表达。

写每个条目前，可以先完成这句话：

> 这个变化让哪类用户现在可以完成什么，或者避免了什么问题？

如果无法回答，它更适合留在内部提交记录中。

## 使用结构化版本组件

Clarify 内置的 `Release` 和 `ReleaseItem` 让版本、日期和变化类别保持稳定结构，同时允许条目内继续使用 Markdown。

```mdx
<Release version="v0.12.0" date="2026-07-25">
  <ReleaseItem title="新增">
    导航组可以声明 `layout: 'blog'`，组内页面会自动继承。
  </ReleaseItem>
  <ReleaseItem title="改进">
    页面可以声明 `layout: 'documentation'`，覆盖所在组的博客布局。
  </ReleaseItem>
</Release>
```

这比用多个 H2/H3 模拟数据结构更可靠：版本标题、发布日期和条目边界都有明确语义，视觉样式也由主题统一维护。

## 给发布页面一个固定编辑流程

<Steps>
  <Step title="收集面向用户的变化">
    从合并记录、问题和迁移说明中提取用户能观察到的变化，排除纯内部重构。
  </Step>
  <Step title="按结果合并条目">
    多个提交共同完成一个能力时，只写一个完整条目；不要把实现步骤逐条暴露给读者。
  </Step>
  <Step title="标记行动要求">
    遇到破坏性变化、弃用或配置迁移时，明确写出受影响范围和下一步，并链接到完整指南。
  </Step>
  <Step title="与版本一起构建">
    在发布前运行文档构建，确认 MDX、内部链接、搜索索引和多语言页面同步可用。
  </Step>
</Steps>

## 博客布局和文档布局各司其职

博客系列适合观点、设计过程和阶段性实践，因此可以在导航 group 上统一设置 `layout: 'blog'`。配置后，组内所有没有手动指定布局的页面自动继承：

```ts
{
  group: '博客',
  layout: 'blog',
  pages: ['blog', 'blog/release-as-documentation', 'changelog'],
}
```

如果其中某一页是高密度参考资料，在 frontmatter 中写 `layout: documentation` 即可覆盖 group。默认布局同样是 `documentation`，名称直接表达它的用途。

## 发布记录应该通向更完整的文档

版本列表负责告诉读者“发生了什么”，指南和参考手册负责解释“怎么使用”。当一个发布条目需要较长代码示例、迁移步骤或完整配置表时，保留一句摘要并链接到独立页面。这样版本列表保持可扫描，长期文档也不会埋在历史版本下面。
